# 窗口与后台准备并行（2026-11-08）

> 本文记录前一阶段的实现和测量。当前正常启动已取消逐文件扫描，最新策略与结果见 [轻量启动与完整诊断](startup-integrity-20261108.md)。

在上一轮缓存优化基础上，运行时准备现在与原生窗口初始化同时执行。本机 Debug 版交叉复测中，启动到界面挂载的中位数由 **10.929 秒降到 10.558 秒**，减少 **0.371 秒 / 3.4%**。这是第二轮优化的增量收益，未把上一轮缓存优化的收益重复计算。

## 执行顺序

Tauri setup 开始后立即启动后台工作线程，执行维护记录审计、Node 检测、必要的中断恢复、运行时选择和文件校验，以及版本准备。同时主线程初始化通知、WebView2 窗口、托盘和深链。

后台准备完成后，通过一次性通道等待主线程的初始化成功信号，再安装缺失运行时或启动后端。主线程不等待后台线程，因此窗口可以正常创建和响应；信号先到时也不会丢失。如果任何 setup 步骤失败，发送端被释放，后台停止后续启动。如果应用已经进入退出状态，同样不会启动后端。

提前产生的检测错误保存在 AppState，加载后的启动页面可以读取，用户重新检测时使用同一套启动流程。版本探测改用现有的进程树管理和输出读取实现，即使 setup 失败导致应用退出，仍在执行的探测进程也会由 Windows Job Object 结束。

更新恢复仍先于运行时选择，文件校验仍先于后端执行，插件预处理仍先于插件挂载。本次没有增加文件校验线程数量，也没有延后业务插件初始化。

## 实测

Windows x64、Node 24.18.0、DSH 0.2.1-rc.2、Debug 构建；同一个隔离 Profile、WebView2 数据目录及包含 63,598 个文件的受管理运行时。两版均包含上一轮版本复用、Node 校验缓存和模块编译缓存。

| 版本 | 轮数 | 窗口可见中位数 | 后端就绪中位数 | 界面挂载中位数 | 文件检查中位数 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 改动前，首次测量 | 3 | 0.651 秒 | 10.978 秒 | 11.259 秒 | 5.333 秒 |
| 并行版 | 5 | 0.639 秒 | 10.271 秒 | 10.558 秒 | 5.222 秒 |
| 改动前，在并行版后复测 | 5 | 0.640 秒 | 10.641 秒 | 10.929 秒 | 5.155 秒 |

以最后一组复测作为主要基线，减少系统预热造成的偏差。后台准备起点从窗口完成后的约 423–472 毫秒，提前到启动后的约 7–10 毫秒。并行版窗口创建约 447–476 毫秒完成，期间 Node 检测和运行时校验已经开始。

每轮退出测试应用并创建新进程，计时前预热。界面挂载检查沿用上一轮的 UI bridge 与 React 根节点条件，并包含轮询和 CDP 观察开销。结果是本机多次测试的描述，不是 Release 安装包、系统冷启动或首次安装的性能保证。文件检查仍占约 5 秒；此次收益主要来自重叠的窗口准备时间。

完整逐轮数据、时间点及原生场景验证保存在 [JSON 报告](startup-parallel-20261108.json)。

## 验证

- Rust 全量测试：261 项通过，5 项按原配置忽略。
- 启动页、启动标题栏、预加载和 UI 状态测试：111 项通过。
- 原生场景：准备先完成、窗口先完成、提前检测错误后修复并重试、setup 失败时取消后端启动、setup 失败时结束仍在执行的版本探测。

`tools/native-startup-parallel-smoke.mjs` 只使用仓库 target 内的隔离测试目录。测试延迟和故障注入仅在显式设置隔离目录的 Debug 程序中启用，Release 不包含这些入口。可在构建后执行：

```powershell
npm run test:startup-parallel -- src-tauri/target/debug/deepseek-harness-desktop.exe
```

性能复测使用已有 `tools/startup-benchmark.mjs`。本次为避免覆盖运行中的开发程序，使用仅修改 Cargo 包名的验证副本，共享依赖构建缓存。
